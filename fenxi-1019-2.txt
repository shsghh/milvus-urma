一句话版本
8 个 SN 的部署没错；错的是建 collection 的时机。8 个"收件口"（vchannel）在建 collection 时就被钉在了 sn0 一个 SN 上，于是 7/8 的 query 没有任何进程认领 → 875 个空结果。

1. 为什么必须 8 个 SN，而不是 8 个 QN
Milvus 3.0 的代码事实（不是配置问题）：

milvus run streamingnode 会同时起一个内嵌 QN（cmd/milvus/util.go:138-141）；
search 那一跳（channel leader / delegator）只发给内嵌 QN（assign_policy_components.go:111 过滤只留 SQN）；
普通 milvus run querynode 永远拿不到 channel，永远收不到 search。
所以你之前的 1SN + 8QN：真正算 search 的只有 1 个进程，另外 8 个 QN 只是"内存被远端读"。"8 个 QN = 8 个 rank"从来没成立过——8 个 rank 必须是 8 个 streamingnode。

2. 875 empty 到底怎么来的（你那条日志就是证据）
collection 有 8 个 shard → 8 个 vchannel（收件口）；
建 collection 的那一刻，每个 vchannel 会被绑到一个 pchannel（channel/manager.go:397-407，按"vchannel 最少"挑 pchannel）；
pchannel 归哪个 SN，取决于那一刻哪些 SN 已注册（以及 etcd 里的旧分配）。你那次全在 sn0；
channel leader 只能落在 pchannel 所在的 SN → 8 个 vchannel 全在 sn0；
而 sn0 只 seed 了 1 片（shard 0），它只对 req_id % 8 == 0 的 query 负责 → 只有 1/8 有答案。
三个数字互相印证：875/1000 ≈ 7/8（空的比例）、main 日志全在 sn0、target shard 全是 0。这不是算法问题，是"谁该回答哪个 query"的分派没有铺开。

3. 我前面几轮改的代码里，确实有两个真 bug（已修）
bug	症状	根因	修法
我加的 preferLocalReaders 打开了本地直读，但线程组还在跑	HnswSearchTask::Create failed → 静默回退原生 → recall 崩到 0.0081 那一半	线程组要求 reader 支持 prepared-wait，LocalGraphReader 不支持	全本地覆盖时不启动线程组，直接 inline RunToCompletion
我把 std::atomic 放进按值返回的类	编译失败（移动构造被删除）	Result<T> 用 Result(const T&) 返回，需要可拷贝	计数器移到 local_io.cpp 文件级原子变量
至于 127.5s vs 5.07s：那是同一份 1SN 部署下"走 URMA 拉向量"和"全本地"的差别（25×），符合预期，但不代表 8 rank 跑通了。

4. 这些脚本各干什么（为什么加）
脚本	干什么	防的是哪个坑
check_8sn.sh	体检：每个 SN 的 seed/pchannel/peer ready/main 数/target 直方图/回退计数	让"875 empty"这类问题 10 秒定位，不用猜
deploy_inst2_true_dist.sh	8 SN 启动（顺序、shardIds=i、dmlChannelNum=8、线程数写死）	用 QN 当 rank、auto 线程爆炸
create_ub_collection.py	建/load 一个 8 shard 的空 collection（ub_gist，pk=100/vector=101）	清元数据后 collection 没了，你的 loadpool.py 会直接报错
bootstrap_ub_collection.sh	先校验 8 个 pchannel 真的摊在 8 个 SN 上，不满足就 exit 3 拒绝建 collection；通过后再 create+load	就是这次踩的坑：顺序错了就再也不想建 collection
recreate_middleware.sh	WIPE_META=1 清 etcd/minio/pulsar	改 dmlChannelNum 必须清元数据，否则旧绑定还在
patches/*.patch	代码修复（读并发、锁、inline、dedupe、编译）	400ms、串行、编译不过
另外一条你可能没意识到的：ub_inject 那套（8 个占位 segment + 传 MinIO + 注入元数据）对 UB 快路径不必要——UB 路径根本不读 segment。它是给"原生兜底"用的，而 8-SN 下兜底本身是错的（每 QN 只有 1/8 数据）。所以清元数据后不用重建那 8 个占位 segment。

5. 所以现在具体做什么（4 条命令）
bash


# ① 清元数据（一次性，会删掉所有 collection）
for p in $(ps -eo pid,args | grep 'milvus run' | grep -v grep | awk '{print $1}'); do kill -9 $p; done
WIPE_META=1 ./recreate_middleware.sh

# ② 起 8 个 SN（顺带 datanode/proxy/segment QN）
./deploy_inst2_true_dist.sh

# ③ 校验 pchannel 摊平 → 建 8 shard 的 collection → load
#    没摊平会直接 exit 3 并告诉你怎么等/重启 mixcoord
./bootstrap_ub_collection.sh

# ④ 发几个 query，然后体检
bash ~/check_8sn.sh
③ 被拦下时（很可能第一次会）：等 60~120s 再跑；还不行就只重启 mixcoord（8 个 SN 都已在线时它会按 8 个节点重算 pchannel），再跑 ③。

6. 怎么判断"这次对了"
看 ③④ 的输出，只要同时成立就是对的：

8 个 SN 的 pchannels seen 各不相同（每个 1 个）；
8 个 SN 都有 UB SearchEntry: main，且 target shard 是 0..7 各一个 SN；
sum(main) ≈ 你发出的 query 数；
没有 falling back to native、没有 HnswSearchTask::Create failed。
如果 2 成立但 3 只有 1/8，那就是 query 侧分摊（Go 的 dedupe key）问题，我来改——那时问题已经从"部署顺序"缩小到"分派逻辑"了。

如果你现在只想先把环境恢复成能跑（别的不动），那就退回 1SN + preferLocalReaders=true：那是你已经测过的 5.07 s / recall 0.936，确定可用。
