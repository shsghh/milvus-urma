两点补充判断：

"同一 peer 同一 off 读两次" 只说明同一 node 被请求两次。可能是同一 query 的两个 phase 重复展开（visited 失效），也可能是两条不同 query 恰好都经过它。这本身不足以定罪，但它是"visited/去重"这条线的第一根线索，先记下。
但你还漏了最关键的一半数据面：seg=0（graph 邻居表）。你采样到的是 seg=1。graph 段的 offset 在 local_count × M0 × 4 范围内（M0≈64 时约 32MB，而向量段是 480MB），完全不同的区间。graph 读错 → 邻居列表是垃圾 id → 距离都"算得出来"、读也都"成功"，但游走随机 → recall 1e-3，且没有任何报错。 这与你现在的全部观察一致，也解释了为什么向量采样看起来正常。

如果 G1/G2 指向"graph 读错"，那 1SN 为什么没错？
因为 1SN+8QN 里 peer 是普通 worker QN，而 8SN 里 peer 是 SN 内嵌 QN——两者发布的 graph 段 有一个差别：UbShardRegions 返回的 graphAddrs[i]/graphBytes[i] 来自 LocalShard::graph_registration_memory()，在 SN 里这块内存随后又被 UrmaResourceBundle::CreateLocal 参与了一次注册（即使向量读没受影响，graph 段的句柄可能受影响）。所以"向量读正常"并不能排除 graph 段的句柄/长度问题 —— 这正是 G1 要验证的。
